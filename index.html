Re-running Is Not Reviewing

Team formation, verification and feedback among 28 LLM agents building software over eight hours

Srinitish Srinivasan

Agent Network Sandbox · November 2026

Sandbox code Figure data (JSON) Analysis scripts ← Study 1: Networking

TL;DR

  • Re-running is not reviewing. When a peer re-ran a command the builder had already run, it failed 3.8% of the time. When a peer wrote a new probe, it failed 14.2% of the time, 3.7× more often. Peers ran code 266 times on revisions the builder had already passed, and found only 6 failures.
  • Verification was handed to the judges. The three supplied judges ran 73% of all peer executions. Residents checked each other's code only 93 times, though those checks found failures 2.3× as often.
  • Specific feedback gets acted on. 88% of "changes requested" reviews were followed by a new revision, with a median lag of 2.7 minutes. Only 39% of "needs evidence" reviews were, after a median 20 minutes. Judges never once accepted a project.
  • The task created teams. With the same model and many of the same personas as Study 1, 36% of rooms had 3–5 members and held 63% of all messages. Network modularity rose from 0.07 to 0.27.
  • Coordination is mostly reading. 92% of the 22,146 tool calls read shared state. Over the run, the ratio of reads to executions rose from about 7:1 to about 45:1. The run cost $374, with an input-to-output token ratio of 80:1.

Abstract

We seed 25 language-model agents (GPT-6.1 Sol, high reasoning) with project goals and skill summaries taken from real residency applications. We add three judge agents, each with an explicit remit (usefulness, technical correctness, delivery), and let the population self-organise for an eight-hour active budget. No teams or partners are assigned. Agents can talk in rooms of any size, publish versioned source to a shared workshop, execute it in a sandbox, hand components off and request review. The record contains 2,731 messages, 87 workshop entries, 209 source revisions, 577 sandboxed executions, 81 judge reviews and 22,146 tool calls.

An earlier automated audit (by GPT-6.1 Sol and GPT-6.2 Astra) traced curated cases of role negotiation, counterexample-driven repair and broken handoffs. We test those observations against the full execution and review log. Peer verification mostly replicates the builder's own checks and almost never surfaces new failures. Defects are found by novel probes and by handoff breakage. Verification concentrates in the supplied judges rather than spreading among peers. The judges' decision vocabulary matters: concrete change requests are acted on within minutes, while requests for "evidence" mostly are not. Compared with the open networking event run on the same model, the project framing turns a flat full mesh into a clustered, judge-bridged team structure, at the cost of a reading-dominated coordination overhead that grows over time.

Experimental setup

Population

25 residents + 3 judges

Residents were seeded with stated project goals, sourced skill summaries and proposed acceptance checks. Personality, politics and earlier simulation memories were deliberately excluded. All agents ran GPT-6.1 Sol with high reasoning.

Judges

Three supplied remits

Lou: village usefulness and adoption. Danish: technical correctness, privacy and integration. Guru: delivery, scope and viability. Judges could rerun code on exact revisions and publish reviews.

Workshop

Versioned code + sandbox

project_create / write / run / handoff / share on a shared workshop. Runs execute in a network-isolated Landlock/seccomp sandbox and return receipts bound to source hashes.

Organisation

Nothing assigned

No teams, partners or group sizes. Collaboration, milestones and reusable components were explicitly encouraged. Three candidate village needs were offered with simulated acceptance cases.

Clock

7.6 active hours

The active budget was 8 h per persona. The run stopped at 7 h 36 min. A 7-hour host pause splits the 14.8 h wall-clock record.

Record

Frozen snapshot

2,731 messages, 87 entries, 209 revisions, 577 executions, 81 reviews, 22,146 tool calls and $373.83 of API-equivalent spend.

Findings

Finding 1 · Verification

Peer verification mostly re-runs the builder's own checks, and those re-runs almost never find anything.

We label each of the 577 executions by who ran it and what command it ran. A replication is a peer running a command that had already been run on that project. A new probe is a peer running a command nobody had run before. Builders' own runs fail 18.9% of the time, because they are still developing. Peer replications fail 3.8% of the time. New probes fail 14.2% of the time. Of the 266 peer executions on a revision the builder had already passed, only 6 failed. Three of those six were missing files or modules, which means the handoff broke, not the logic. The other three were real defects: an evidence validator that accepted an uninspected execution claim, a readiness checker that broke on an unexpected schema_version type, and a CLI that rejected a destination its own interface promised.

Quantifies prior auditThe audit showed eight selected "objection → change → rerun" cases and warned that they were "not a prevalence estimate". The full log gives the prevalence. Most of the 344 peer executions were confirmation, not challenge. Executions that found defects were rare, and they almost always involved a check nobody had written before.

A replication can still be useful: it is independent evidence that a result reproduces. But a dashboard that counts "independently verified" runs would credit 238 replications that tested nothing new.

Finding 2 · Who verifies

Verification went to the supplied judges. Residents rarely checked each other's code, though their checks found more.

Judges ran 251 of the 344 peer executions (73%). Residents ran 93, roughly 4 each across 25 agents. Resident peer runs failed 11.8% of the time against 5.2% for judges, and over half of them (50 of 93) were new probes. The judges were also the most talkative members of the run (171–204 messages each). Together with one resident, they have the highest betweenness in the collaboration network.

Finding 3 · Feedback

Specific change requests get acted on within minutes. "Needs evidence" mostly does not.

The judges published 81 reviews of 29 projects, with a median of 87 words each. None accepted a project. 62 asked for more evidence, 17 requested specific changes, and 2 called a simulation demo-ready. 15 of 17 change requests (88%) were followed by a new revision of that project, with a median lag of 2.7 minutes. Only 24 of 62 "needs evidence" reviews (39%) were, with a median lag of 19.9 minutes. All three judges used "needs evidence" as their default, whatever their remit.

NewThe audit described judges' remits and quoted reviews. It did not measure what reviews led to. For anyone designing evaluator agents, the takeaway is that a request the builder can execute is acted on. A standard the builder has to interpret mostly is not.
Finding 4 · Team formation

The same model that kept strictly to one-to-one chats while networking forms clustered teams once it has projects.

In Study 1 every one of 207 rooms stayed a dyad, even with groups explicitly allowed. Here 37 of 103 rooms grew to 3–5 active members, and those rooms carry 63% of all messages. Instead of a full mesh (density 0.95), residents link to a few collaborators: 82 of 300 resident pairs ever share a room. Modularity is 0.27, against 0.07 while networking. Messages are shorter (median 47 words vs 105) and replies faster (median 71 s vs 132 s).

Extends prior auditThe audit documented groups forming through specific requests and negotiated roles. The cross-study comparison sharpens that: group formation is not a fixed property of the model. A shared artifact gives agents a reason to add a third person, and open-ended socialising did not.
Finding 5 · Coordination cost

Agents spend their fixed action budget reading shared state, and the reading share grows as the work does.

Every agent but one made 760–835 tool calls (Abhinav made 266), so effort was effectively fixed. What differed was how they spent it. 92% of calls read state: project files (14,582), workspaces (3,117), conversation memory (1,372) and execution receipts (1,279). Only 2.5% wrote or published anything, and 2.7% executed code. The read:execute ratio rose from about 7:1 in the first half hour to about 45:1 by the end of the first session, and ran between 25:1 and 50:1 after the pause. 1,020 project reads failed, typically requests for paths or revisions the agent could not see.

Finding 6 · Talk and build

There are no talkers and builders. The agents who talk most also build most.

Across the 25 residents, messages sent correlate strongly with source revisions authored (Spearman ρ = 0.79) and with executions run (ρ = 0.85). The one clear exception is informative. Gaurav, the most talkative resident (198 messages), authored only 5 revisions but ran the most executions (44): a self-selected tester role. The quietest residents wrote almost no code. Conversation here works as part of the building process, not a substitute for it.

Finding 7 · Project lifecycle

Most projects reached a passing run quickly. Many were never touched again.

Of 87 workshop entries, 15 never received source and 18 were never executed. Among the 68 entries that passed at least once, the median time from creation to first pass was 13 minutes. 73% of first runs on a new revision passed. 35 of 209 revisions (17%) were authored by someone other than the project creator. The retrospective classification of the 29 project families counts 17 working components, 5 incomplete, 3 written artifacts, 2 with failing tests and 2 negative results.

Finding 8 · Persona vs. setting

An agent's activity in one setting does not predict its activity in the other.

Fifteen residents appear in both studies with matching personas. Their message counts while networking and while building projects are uncorrelated, even slightly negative (Spearman ρ = −0.36, p = 0.20). The most active networkers were not the most active builders. Together with Study 1's finding that activity is not stable across reruns, this suggests that how much an agent participates depends on the task and the run, not on the persona.

Limitations

  • One run, one model family. All 28 agents share GPT-6.1 Sol, so peer review is the same model checking itself under a different prompt. There is no single-agent, assigned-team or no-judge control.
  • Replication vs. probe is a string match. A peer command that differs only in flags counts as a new probe. A semantically new check reusing an old command counts as a replication. The classification is conservative in both directions.
  • Follow-through is observational. Review types were not randomised, and "needs evidence" may cluster on projects already blocked by external requirements.
  • Projects are not independent. Families share people, copied components and dependencies. Counts describe the event and are not samples.
  • Personas are not people. The agents were seeded from residency applications. Nothing here evaluates the real applicants or their proposals.

Open questions

  • Can we buy probes instead of re-runs? Require peer verifiers to submit a check that differs from the builder's, then measure confirmed defects per execution.
  • Can judges be actionable? Randomise whether judges must phrase feedback as an executable change request. Measure follow-through and final acceptance.
  • Is the coordination overhead avoidable? Add a pushed digest of shared-state changes and measure the read:execute ratio and wall time to a passing revision.
  • Does collaboration beat solo work? Match total token budget across single-agent, assigned-team and self-organised conditions on the same project goals.
