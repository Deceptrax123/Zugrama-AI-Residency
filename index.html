Zugrama Residency

How AI agents chose collaborators, divided the work, and built software together.

Explore the findings Browse all 29 projects

Abstract

How do AI agents turn a project idea into work that others can build on and check? Zugrama Residency was a simulated software workshop in which 25 GPT-6.1 Sol agents brought project goals drawn from residency applications. They had 7.6 active hours to find collaborators, decide what to build and divide the work. Three judge agents reviewed their work.

We traced how proposals became assignments and how collaborators handled changes and disagreements. The analysis covers 29 projects, 87 workshop entries and 577 recorded code runs. Of the 72 entries with saved source, 23 had contributions from more than one source author. Agents attached test results to 22 of their 24 explicit version handoffs.

Seventeen projects showed a tested component at the end of the workshop. Tuhin handed over a version of a Hindi–English text adapter that Anuj tested successfully in his memory tool. In a digital-goods checkout project, a payment repair passed 19 tests on a review copy. After the team tried to apply the repair to the main copy, its final 19-test run produced 16 failure reports. Tracing each check to the version used shows which pieces collaborators could reproduce and which still needed work.

Study design

Agents could discuss ideas, save code in workshop entries, run a saved version and hand a specific version to a collaborator. A project could span several entries, including a main build, a component and a review copy. The catalogue also includes written work saved outside the code workshop.

We linked each project’s conversation to its saved work and used run receipts to identify the exact source that was tested. That gives readers a way to follow a proposal through to a source change, a test on the original version or a check in the receiving project.

Research questions

  • How did collaborators find each other and divide the work?
  • How did they keep track of changes and hand off versions?
  • Where did they disagree about the design, the code or what the tests showed?

How teams kept track of changes

The workshop kept a numbered history for every entry. Agents built their own working agreements around it. They divided responsibility by file, handed over specific versions, and kept tests tied to the source they had actually run.

Save against the latest version
Every edit named the version it started from. The workshop would reject a save if the source had changed in the meantime. A successful save recorded the author and a fingerprint of the exact files. The project explorer shows what each version added, changed or removed.
Agree on who edits which files
Aditya kept the civic workflow separate from Ganesh’s intake files. Mahboob added contribution records in separate files after reading the workflow. That split gave each agent a defined place to work and a shared interface to test. See how the team divided the work.
Hand over a version someone can check
Agents handed over specific versions 24 times across 20 entries. Twenty-two handoffs included test results, with 26 result attachments in total. When Anuj reused Tuhin’s text adapter, Tuhin approved one snapshot and Anuj tested the receiving copy. See the adapter handoff.

Twenty-five entries got their first source version in the first half hour. The next half hour had the most later saves, 27. Seven version handoffs and all six room shares happened in the first half hour.

Across the workshop, agents opened 87 entries and saved source in 72. Of 137 later saves, 71 only added files, 59 changed at least one existing file, and 7 saved identical source.

Who changed the code
15 agents saved 35 versions on entries someone else opened. On 23 of the 72 entries with source, more than one agent saved a version.
How it reached collaborators
Owners moved six entries from private access into a room where collaborators could inspect the saved work.
What got checked
The workshop recorded 577 runs, including failures. The project explorer counts runs and handoffs against the version they used.

Where collaborators disagreed

Some disputes were about code and test expectations. Others were about whether a proposed feature was worth building or what a passing test entitled the team to claim.

Which should change, the code or the test?

A civic dashboard test expected a restarted report to say “submitted.” The reporting core called that state “reported.” Ganesh kept the core behavior, corrected the test expectation and reran the suite. The previous failure stayed in the record.

Who would use the proposed feature?

Hiro and Anuj had pieces for sharing approved memories, but Aditya could find no demonstrated need for a memory lookup in the civic workflow. He declined that integration. The civic team continued with the reporting work it could justify.

Can a passing component close the review?

Danish closed a technical review of the civic contribution component after the scoped checks passed. Guru asked for those checks to be separated from evidence about how the whole tool would be used. The broader review still asked for evidence.

Does another dependency belong in the project?

The algae-controller team discussed adding a storage adapter. Bhuvan kept the exchange local for the synthetic controller tests. The team kept the design review as a contribution and left the storage integration outside the agreed scope.

Appendix

Sources and counting rules

The catalogue combines the frozen project snapshot with the prior project overview and project-family review. Contribution counts come from source versions, runs, judge reviews and successful sharing and handoff calls. File changes compare each saved version with the previous one. The evidence cards link selected findings to frozen conversations, workspace drafts, reviews and code runs. Code-run receipts match the saved source version by fingerprint. Exit status reports whether the command completed successfully. The finding explains what the run actually demonstrated. The timelines count active workshop hours from the start. The roles beside each project come from the earlier qualitative review and can include contributions made in conversation or in another entry.

Written work without a workshop entry appears in the catalogue with its documented collaborators. The case studies and disagreement tally use selected exchanges. The tally describes the selected exchanges and has no run-wide denominator.

The opening figure uses one outcome per project from the project-family review. “Component tested” records a passing check on a piece of the proposed work. “Work unfinished” means a required delivery or check was still pending. “Tests still failing” describes a retained suite with failures on the main work. “Negative result” describes a check that went against the project’s research hypothesis. “Written work” covers proposals, essays and reports retained as documents.

The snapshot also records 1,780 agent-written messages and 81 judge reviews. Message totals exclude 951 automated platform notices. One resident stopped receiving regular turns after three active hours. The prompt told agents to distinguish drafts, tested work and outside validation.
